Subagent visibility UI improvements

A concise discussion aid for improving how pi-tmux-subagents shows what child agents are doing, while preserving the extension's one-slot, low-surveillance UI constraints.

The widget has only a few lines. Spend them on what is blocked, what broke, and what may be stale.

Problem

The current UI is compact, but the hierarchy is too flat.

The code already tracks attention, errors, heartbeat age, usage, result files, and fresh Agent Hub metadata. The display does not yet use that information consistently enough to make scanning easy.

Blocking context is missing.
The default widget can show needs input, but it should also show the actual heartbeat.attention.message.
Routine and urgent rows look similar.
✸ needs input and ⟳ running need stronger separation in text order, color, and detail choice.
Motion is ambiguous.
active 6m ago is technically true, but the user needs to know whether that means normal long-running work or possible stall.

Guardrails

Better visibility should not become noisy surveillance.

The strongest UI direction keeps the existing privacy and lifecycle boundaries visible in the design itself.

One slot

Summary, details, peek, and view entry points still replace each other. The parent UI should not accumulate competing status surfaces.

Safe default text

Default user-facing rows avoid full paths, raw commands, model names, and pane previews. Result filenames are enough for compact surfaces.

First-class signals only

needs input comes from explicit heartbeat.attention. Summaries are fresh read-only metadata; no model calls or pane scraping.

✸ needs input ✗ error ⟳ running ✓ idle · done

Default widget direction

Promote blocking states before adding more rows.

The default widget should answer the first triage question: does any child need the parent, fail, or look stuck?

Interactive view direction

/subagents view should feel like a small control room, not a longer table.

The grouped manager is the right skeleton. It needs stronger row rhythm, truthful key affordances, and a peek panel that carries the same sanitized context as the widget.

Signal model

Use three signal tiers: intervention, progress, and retrieval.

This keeps information dense without making the widget verbose. Each tier maps to data the extension already has or reads safely.

01 · Intervention

Needs input or error

Pin first. Show the question or short error reason. These rows explain why the parent must act.

02 · Progress

Stage and heartbeat age

Show fresh stage/status metadata when present, then activity age. A soft no activity Xm label is useful only when heartbeat silence crosses a clear product threshold, such as five minutes.

03 · Retrieval

Result filename and usage

For done/idle rows, make it easy to know that output exists without printing full result paths in the default UI.

Default widget detail budget

Each row gets one primary detail: question or error first, otherwise fresh semantic status, otherwise task/result. Running rows stay concise; richer task, lineage, and attach details belong in /subagents view.

Signal precedence

heartbeat.attention and job errors override everything. Fresh Agent Hub metadata can explain progress, but it should not mask a stale heartbeat or replace explicit child attention.

Known source fields: heartbeat.attention, heartbeat.updatedAt, latestTurn.messagePreview, result basenames, usage, and fresh Agent Hub goal/status/nextStep/stage.

Recommended direction

Choose an attention-first dashboard, not a bigger transcript.

Most valuable bundle

  • Show actual attention questions and short error reasons in the default widget.
  • Separate needs input, error, running, idle, and done visually and consistently.
  • Let /subagents view handle richer triage: grouped rows, sanitized peek, and truthful action keys.

Boundaries to keep

Not a pane scraper
Do not infer progress from raw tmux output.
Not a model summarizer
Only reuse fresh metadata written elsewhere.
Not a tree browser yet
Lineage can remain a peek/detail field until nested usage is common.
Not an infinite history
Keep stopped/completed rows bounded and low-salience.
